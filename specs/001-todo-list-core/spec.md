## User Scenarios & Testing *(mandatory)*

### User Story 1 - タスクを追加する (Priority: P1)

ユーザーとして、新しいタスク内容を入力し、ToDo リストに追加できる。追加後は
タスクが登録日時付きで一覧に表示され、次に取り組むべき作業をすぐ確認できる。

**Why this priority**: タスクを登録できなければ ToDo アプリとして成立しないため。

**Independent Test**: タスク未登録の状態で 1 件以上のタスクを追加し、一覧表示に
反映され、再読み込み後も残っていることを確認できれば、このストーリーは独立して
価値を提供する。自動テストでは追加処理と保存処理を単体テストで検証し、主要フロー
として追加から再読み込み後の表示維持までを E2E テストで確認する。

**Acceptance Scenarios**:

1. **Given** タスクリストが表示されている、**When** ユーザーが有効なタスク名を入力して追加する、**Then** 新しいタスクが未完了状態で登録日時付きで一覧に表示される
2. **Given** 新しいタスクが追加済みである、**When** ユーザーが画面を再読み込みする、**Then** 追加したタスクの内容、完了状態、登録日時が保持されたまま表示される

---

### User Story 2 - タスクの状態を管理する (Priority: P2)

ユーザーとして、登録済みタスクを完了済みまたは未完了に切り替え、現在の進捗を
把握できる。

**Why this priority**: タスクの消化状況を管理できないと、リストの実用性が大きく
下がるため。

**Independent Test**: 既存タスク 1 件に対して完了操作と未完了操作を行い、表示状態
および保存状態が切り替わることを確認できれば、このストーリーは独立して検証できる。
自動テストでは状態遷移ロジックを単体テストで検証し、主要フローとして完了切替の
画面操作を E2E テストで確認する。

**Acceptance Scenarios**:

1. **Given** 未完了タスクが 1 件ある、**When** ユーザーがそのタスクを完了に切り替える、**Then** タスクが完了済みとして表示される
2. **Given** 完了済みタスクが 1 件ある、**When** ユーザーがそのタスクを未完了に切り替える、**Then** タスクが未完了として表示される

---

### User Story 3 - タスクを整理して見る (Priority: P3)

ユーザーとして、不要なタスクを削除し、さらに「すべて」「未完了」「完了済み」で
絞り込んで表示できる。これにより、必要なタスクだけに集中できる。

**Why this priority**: 追加と状態管理の次に、一覧を維持しやすくする整理機能が必要
になるため。

**Independent Test**: 複数の状態の異なるタスクを用意し、削除とフィルタ切替を行って、
表示対象が期待通りに変わることを確認できれば、このストーリーは独立して価値を
提供する。自動テストでは削除とフィルタ判定を単体テストで検証し、主要フローとして
削除とフィルタ切替の画面反映を E2E テストで確認する。

**Acceptance Scenarios**:

1. **Given** 複数のタスクが登録されている、**When** ユーザーが特定のタスクを削除する、**Then** そのタスクは一覧から消え、再読み込み後も復元されない
2. **Given** 未完了と完了済みのタスクが混在している、**When** ユーザーが表示フィルタを「完了済み」に切り替える、**Then** 完了済みタスクだけが表示される
3. **Given** フィルタが「未完了」に設定されている、**When** ユーザーが表示フィルタを「すべて」に切り替える、**Then** すべてのタスクが表示される

### Edge Cases

- タスク名が空文字、空白のみ、または極端に長い場合、システムは追加を拒否し、
  ユーザーに入力が無効であることを明確に示す
- 保存済みタスクが 0 件の場合、システムは空の一覧を表示し、操作不能ではない
  初期状態を維持する
- 選択中フィルタに一致するタスクが 0 件の場合、システムは空表示を保ちつつ、
  フィルタ状態が分かるようにする
- 保存データが壊れている、または読み込めない場合、システムは画面を壊さず、
  安全な初期状態で利用を継続できる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、ユーザーが新しい ToDo アイテムを追加できる入力手段と
  実行操作を提供しなければならない
- **FR-002**: システムは、有効な ToDo アイテムを追加した直後に一覧表示へ反映
  しなければならない
- **FR-002a**: システムは、ToDo アイテムの登録時に登録日時を記録し、各アイテムに
  対して `YYYY/MM/DD HH:SS` 形式で一覧表示しなければならない
- **FR-003**: システムは、各 ToDo アイテムを完了済みまたは未完了に切り替え
  られなければならない
- **FR-004**: システムは、登録済みの ToDo アイテムを削除できなければならない
- **FR-005**: システムは、ToDo リスト全体を一覧表示しなければならない
- **FR-006**: システムは、表示対象を「すべて」「未完了」「完了済み」で
  切り替えられなければならない
- **FR-007**: システムは、ToDo アイテムの内容と完了状態をページ再読み込み後も
  維持しなければならない
- **FR-007a**: システムは、ToDo アイテムの登録日時をページ再読み込み後も維持
  しなければならない
- **FR-008**: システムは、無効な入力で ToDo アイテムを登録してはならず、
  ユーザーに修正すべきことを伝えなければならない
- **FR-009**: システムは、保存済みデータが存在しない場合でも正常に初期表示
  しなければならない
- **FR-010**: システムは、現在選択中のフィルタ状態を利用者が認識できるように
  表示しなければならない
- **FR-011**: システムは、追加、完了切替、削除、フィルタ切替、再読み込み後の
  状態維持に関する主要ロジックを単体テストで検証できる構成でなければならない
- **FR-012**: システムは、主要ユーザーフローである追加、完了切替、削除、
  フィルタ切替、再読み込み後の状態維持について E2E テストで検証可能で
  なければならない

### Constitution Constraints *(mandatory)*

- **CC-001**: 追加、完了切替、削除、フィルタ切替の主要操作は、一覧画面から少ない
  手順で実行できるシンプルな UI として記述する
- **CC-002**: 永続化対象は ToDo アイテムの内容、完了状態、必要に応じて表示
  フィルタ状態とし、再読み込み後も継続して利用できることを前提とする
- **CC-003**: 実装はバニラ JavaScript とブラウザ標準 API を前提とし、
  フレームワーク導入は本仕様の対象外とする
- **CC-004**: モバイルとデスクトップの双方で主要操作が横スクロールなしに行える
  画面構成を前提とする
- **CC-005**: キーボード操作、フォーカス可視性、セマンティックな構造、
  色以外での状態表現を考慮した仕様とする
- **CC-006**: 本仕様書は日本語で記述し、英語は識別子や UI ラベル候補など
  やむを得ない箇所に限る

### Key Entities *(include if feature involves data)*

- **ToDoアイテム**: ユーザーが管理する単一のタスク。主な属性は識別子、表示名、
  完了状態、登録日時、作成順序
- **表示フィルタ**: 一覧に表示する ToDo アイテムの条件。値は「すべて」
  「未完了」「完了済み」
- **保存済みリスト状態**: 永続化された ToDo アイテム群と表示設定をまとめた
  利用状態

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 初回利用者が、説明を読まなくても 1 分以内に ToDo アイテムを
  1 件追加できる
- **SC-002**: 追加、完了切替、削除、フィルタ切替の各操作は、操作後すぐに一覧へ
  反映されたと認識できる
- **SC-003**: 主要ユーザーフローである「追加」「完了切替」「削除」「フィルタ切替」を
  想定利用者の 90% 以上が初回試行で完了できる
- **SC-004**: ページ再読み込み後も、直前に保存された ToDo アイテムと完了状態が
  100% 再現される
- **SC-005**: 一覧上の各 ToDo アイテムについて、利用者が登録日時を
  `YYYY/MM/DD HH:SS` 形式で一貫して判別できる
- **SC-006**: 単体テストで主要ロジックの検証を行い、主要ユーザーフローについては
  E2E テストが継続的に成功する

## Assumptions

- 利用者は単一端末の単一ブラウザ内で ToDo を管理する
- 認証、共有、期限設定、優先度設定、検索、並べ替えは今回のスコープ外とする
- 永続化にはブラウザの `localStorage` が利用可能であることを前提とする
- ネットワーク接続がなくても主要機能は利用できる前提とする
- アプリは個人利用を想定し、同時編集や複数ユーザー間同期は扱わない
